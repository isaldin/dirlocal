# 0001. Журнал изменений и формат курсора

- Статус: предложено (фаза 0, 2026-10-28)
- Проверено на: Directus 12.5.1, Postgres 17

## Контекст

Как Directus 12.5.1 эмитит события (по `@directus/api/dist/services/items.js` и `emitter.js` из образа `directus/directus:12.5.1`):

| событие | meta | когда |
| --- | --- | --- |
| `items.create` | `{ payload, key, collection }` | после коммита транзакции |
| `items.update` | `{ payload, keys, collection }` | после коммита; `updateByQuery`/`updateMany` — один payload на все keys |
| `items.delete` | `{ payload: keys, keys, collection }` | после коммита |

context: `{ database, schema, accountability }`, где `database` — пул, а не транзакция.

Что из этого следует:

1. **`emitAction` не ждёт обработчиков** (`emitAsync(...).catch(log)`). Запись в журнал идёт после коммита и асинхронно. Если Directus упадёт между коммитом и вставкой, изменение потеряется.
2. **Порядок в журнале не равен порядку коммитов.** `createMany` из двух заметок (1, 2) записался в журнал как 2, 1: обработчики выполняются параллельно.
3. **Дырки в последовательности.** Id выдаётся sequence при вставке, а видимым становится при коммите. Вставка с id=11 может стать видимой раньше, чем вставка с id=10. Клиент, получивший курсор 11, навсегда пропустит 10.
4. Filter-хуки не подходят для атомарной записи: у `update` и `delete` filter выполняется **до** транзакции, на `this.knex`. В транзакции работает только filter у `create`, и в нём ещё нет ключа.
5. Мимо журнала проходят: вызовы с `emitEvents: false`, прямой SQL, **каскады на уровне БД** (проверено: удаление задачи с `ON DELETE CASCADE` удалило заметку без события).
6. У системных коллекций событие другое: `files.create` вместо `items.create` (`eventScope = collection.substring(9)`). Для `directus_files` нужны отдельные подписки.
7. `updateBatch` вызывает `updateOne` внутри внешней транзакции. Action может сработать до её коммита, и при откате в журнале останется фантомная запись. Это безвредно: pull перечитывает текущее состояние.
8. `server.start` — это action без await, на нём таблицы создавать нельзя (гонка с запросами). Используем init `app.before` (его ждут) плюс мемоизированный `ensureTables()`, который вызывается перед каждой записью. После hot-reload расширения `app.before` повторно не срабатывает.

## Решение (предлагаемое)

- Курсор — `dirlocal_changes.id` (bigint), непрозрачное число для клиента.
- **Окно оседания:** pull отдаёт только записи с `created_at <= now() - DIRLOCAL_SETTLE_MS` (по умолчанию 2000 мс, время БД). Каждая вставка в журнал — один autocommit-оператор, так что дырка живёт миллисекунды; окно её закрывает без привязки к конкретной СУБД. Цена — задержка доставки около 2 с.
- Повторная доставка безопасна: pull отдаёт текущее состояние записи под правами, а не дельту. Поэтому перекрытие окон допустимо, пропуск — нет.
- Ошибка вставки логируется через `logger.error` с коллекцией и ключами.
- Потери при падении и изменения мимо Directus закрываем сверкой по `date_updated`. Её стоит поднять из фазы 4 в фазу 2.
- Каскады: в фазе 1 на filter `items.delete` (до транзакции) собирать ключи дочерних записей в отслеживаемых коллекциях по связям с `on_delete: CASCADE`, а в action журналировать их как `d`. Альтернатива — требовать `SET NULL` и документировать.

## Последствия

- Курсор монотонен и пригоден для `410 Gone` после компактизации.
- Гарантия «не пропустить» держится на окне оседания. Если вставка дольше окна (перегрузка БД), пропуск возможен. Нужен интеграционный тест с искусственной задержкой.
