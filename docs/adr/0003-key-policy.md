# 0003. Политика ключей

- Статус: предложено (фаза 0, 2026-10-28)

## Решение

- В журнале `item_key` хранится строкой (`String(key)`), в протоколе `key` тоже строка. Тип ключа клиент берёт из схемы `/fields`.
- **UUID-ключ:** клиент генерирует UUID v4 офлайн и отправляет его в `create`. Directus принимает переданный PK, сервер ключ не меняет.
- **Integer autoincrement:** клиент создаёт временный ключ `local:<uuid>`. В ответе push приходит `server_key`, клиент переписывает ключ и ссылки на него (M2O) в локальной БД и outbox по таблице `client_key → server_key`.
- Ссылки на ещё не отправленную запись внутри одного батча push разрешаются на сервере по порядку мутаций: create идёт раньше, и `server_key` подставляется в следующие мутации батча.
- Рекомендация в документации — UUID-ключи для офлайн-коллекций. Integer поддерживается, но сложнее.

## Последствия

- В dev-seed есть коллекция `notes` с integer PK — специально для проверки этой ветки.
- Строковые ключи, отличные от UUID (ручной ввод), считаются «клиент задаёт ключ» и идут по ветке UUID.
