# 0003. Политика ключей

- Статус: предложено (фаза 0, 2026-10-28); пересмотрено в фазе 2, 2026-10-29

## Решение

- В журнале `item_key` хранится строкой (`String(key)`), в протоколе `key` тоже строка.
- **Клиент всегда создаёт запись с UUID v4** и отправляет его как `key` в `create`. Тип первичного ключа клиент не знает: `/fields` недоступен API-only пользователям (plan §7).
- **Сервер решает по схеме.** Первичный ключ `integer`/`bigInteger`, а `key` не целое число — запись создаётся без ключа, сервер выдаёт свой и возвращает `server_key`. Иначе (`uuid`, строковый ключ) UUID клиента становится ключом записи, `server_key` не возвращается.
- По `server_key` клиент переписывает у себя ключ строки, ссылки на неё в полях верхнего уровня других строк и неотправленные мутации outbox.
- Ссылки на ещё не отправленную запись внутри одного батча push разрешает сервер: create идёт раньше, и `server_key` подставляется в `key` и значения полей следующих мутаций батча.
- Рекомендация в документации — UUID-ключи для офлайн-коллекций. Integer поддерживается, но переписывание ссылок на клиенте проходит по всем строкам.

## Изменения относительно первой версии

Было: клиент берёт тип ключа из `/fields` и для integer создаёт временный ключ `local:<uuid>`. `/fields` API-only пользователям недоступен, а префикс не нужен: сервер сам видит тип ключа, а UUID не совпадёт ни с одним integer-ключом.

## Последствия

- В dev-seed есть коллекция `notes` с integer PK — специально для проверки этой ветки.
- Строковый ключ, заданный приложением явно (ручной ввод), идёт по ветке UUID: клиент передаёт его как `key`.
