# 0002. Политика конфликтов v1

- Статус: предложено (фаза 0, 2026-10-28); базовое решение — журнал решений плана от 2026-10-22

## Решение

- Клиент отправляет `base_version` — максимальный `version` записи, известный ему на момент правки.
- Конфликт — когда в `dirlocal_changes` по `(collection, item_key)` есть записи с `id > base_version`, `actor` у них не равен текущему пользователю, и `fields` пересекаются с ключами `patch`.
- **Побеждает сервер:** конфликтные поля не применяются. Непересекающиеся поля из `patch` применяются через `ItemsService.updateOne`. Клиент получает `status: "conflict"` и `conflicts: [{ field, server_value }]`.
- `delete` против изменённой после `base_version` записи — конфликт без применения.
- `update`/`delete` записи, удалённой на сервере (`op = d` после `base_version`), — `rejected`, клиент удаляет запись локально.
- Правки самого пользователя с другого устройства (тот же `actor`) конфликтом v1 не считаются, применяется last-write-wins. Это осознанное упрощение.

## Обоснование

`fields` в журнале надёжен (проверено в фазе 0): `items.update` отдаёт payload, при массовом update — общий для всех ключей. Этого хватает для пересечения по полям без diff значений.

## Последствия

- DoD фазы 2 («правка одного поля с двух устройств не затирает другое») выполняется: разные поля не пересекаются.
- Поле-уровневое слияние значений (v2) и CRDT — в фазе 4.
