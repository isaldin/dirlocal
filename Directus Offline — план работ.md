# Directus Offline — план работ

> Рабочий документ для сессий в Claude Code. Обновлять по мере принятия решений: секции «Открытые вопросы» и «Журнал решений» в конце.

## 1. Что делаем и зачем

**Продукт:** офлайн-режим для мобильных (а затем веб-) приложений на Directus, который уважает права Directus и не требует переписывать бэкенд.

**Проблема.** Directus 12.x не даёт из коробки: дельта-синхронизацию («что изменилось после курсора X»), tombstones удалённых записей, официальный React Native SDK, очередь офлайн-мутаций. Каждая команда собирает это сама. Готовые sync-движки (PowerSync, ElectricSQL) читают Postgres напрямую и теряют модель прав Directus.

**Ключевая идея.** Всё через хуки и `ItemsService` с `accountability` пользователя:

- изменения логируются action-хуками в собственную таблицу журнала (это даёт tombstones);
- при pull записи перечитываются под правами пользователя — что не вернулось, уходит клиенту как `delete` (запись удалена ИЛИ вышла из видимости);
- push применяется через `ItemsService`, поэтому права, валидация, flows и хуки работают штатно.

**Целевые метрики на 12 месяцев:** 300–1000 звёзд, 1–3k npm-скачиваний/нед., 20–50 команд в проде, листинг в Directus Marketplace, упоминание командой Directus. Первый референс-пользователь — собственное приложение автора в проде.

## 2. Ограничения и контекст среды

- Directus **12.5.0** (октябрь 2026); dev-окружение на 12.5.1, 12.6.0 вышел 2026-10-27 — проверить перед обновлением. Проверять breaking changes в 12.x перед каждым релизом.
- Расширения ставятся только через Marketplace или запекаются в Docker-образ (с 12.1.0 `npm`/`npx` в контейнере не работают).
- С 12.4.0 неактивные коллекции отвечают `COLLECTION_INACTIVE` — клиент должен трактовать как «коллекция выпала из синка», не как сбой.
- Официальный `@directus/cli` (d6s) уже использует слово `sync` для схемы/настроек — **в названиях слово `sync` не используем**, используем `offline` / `local`.
- Нельзя опираться на фичи конкретной БД (триггеры, логическую репликацию): Directus поддерживает несколько СУБД. Только хуки.
- Клиент: Expo SDK последний стабильный, `expo-sqlite`, `@directus/sdk` для auth/REST/WebSocket.

## 3. Название

Рабочее кодовое имя пакетов: `dirlocal` (заменить после проверки доступности на npm и GitHub).

- `directus-extension-dirlocal` — серверное расширение (bundle: hook + endpoint + schedule)
- `@dirlocal/core` — движок синхронизации без привязки к платформе
- `@dirlocal/expo` — адаптер для Expo (expo-sqlite, хуки React)
- `@dirlocal/web` — адаптер для веба (позже; IndexedDB или wa-sqlite)

Проверить перед фиксацией: npm, GitHub org, домен, отсутствие конфликта с торговой маркой Directus (бренд не должен строиться на слове Directus — см. историю expo-open-ota → xprem).

## 5. Модель данных на сервере

Таблицы создаются расширением при старте, если отсутствуют (через `database` из контекста хука, knex). Префикс `dirlocal_`.

### `dirlocal_changes` — журнал изменений

| поле | тип | назначение |
| --- | --- | --- |
| id | bigint autoincrement | глобальный монотонный курсор, он же версия записи |
| collection | string | коллекция |
| item_key | string | первичный ключ как строка |
| op | `c` / `u` / `d` | операция |
| fields | json | список изменённых полей (для слияния при конфликте) |
| actor | uuid null | пользователь, сделавший изменение |
| created_at | timestamp | время |

Индексы: `(id)`, `(collection, item_key)`, `(collection, id)`.

### `dirlocal_applied` — идемпотентность push

| поле | тип |
| --- | --- |
| mutation_id | uuid pk |
| user_id | uuid |
| result | json null (ключ сервера, ошибка, конфликты; пусто, пока мутация применяется) |
| created_at | timestamp |

### Настройки — переменные окружения Directus

Не коллекция Directus: на Core каждая коллекция тратит один из 25 слотов (ADR 0004). Таблицы `dirlocal_*` создаются без записи в `directus_collections` и в лимит не входят.

| переменная | по умолчанию | назначение |
| --- | --- | --- |
| `DIRLOCAL_COLLECTIONS` | — | синхронизируемые коллекции через запятую |
| `DIRLOCAL_RETENTION_DAYS` | 30 | срок хранения промежуточных записей журнала |
| `DIRLOCAL_MAX_BATCH` | 500 | лимит записей в ответе pull |
| `DIRLOCAL_SETTLE_MS` | 2000 | окно оседания журнала (ADR 0001) |

## 6. Контракт API

Все эндпоинты требуют авторизацию Directus; `accountability` берётся из запроса.

### `GET /dirlocal/pull?cursor=<id>&collections=a,b&limit=500`

1. Если в журнале есть маркер смены прав (`collection = '$permissions'`) с `id > cursor` — `410 Gone`, `reason: "permissions_changed"`: клиент делает snapshot заново. Маркер пишется при изменении `directus_permissions`, `directus_policies`, `directus_access`, `directus_roles` и при смене `role`/`status`/`policies` пользователя.
2. Если `cursor` больше максимального `id` журнала — `410`, `reason: "cursor_ahead"` (БД восстановлена из бэкапа).
3. Выбрать `dirlocal_changes` с `id > cursor` по запрошенным коллекциям и с `created_at <= now - DIRLOCAL_SETTLE_MS`, `ORDER BY id`, лимит.
4. Схлопнуть до последней записи на `(collection, item_key)`.
5. **Все** ключи (включая `op = d`) перечитать `ItemsService.readMany(keys, { fields: ['*'] })` под accountability. Журнал — это «ключи, которые могли измениться», а `op` — подсказка; поэтому фантомные записи безвредны.
6. Что вернулось — `upsert`, что нет — `delete`. Нет права чтения коллекции — все её ключи `delete`.
7. Коллекция неактивна (`COLLECTION_INACTIVE`) — её имя в `inactive`, изменений по ней нет, курсор идёт дальше.

Ответ:

```json
{
  "changes": [
    { "collection": "tasks", "key": "…", "op": "upsert", "version": 1234, "data": { … } },
    { "collection": "tasks", "key": "…", "op": "delete", "version": 1240 }
  ],
  "next_cursor": 1240,
  "has_more": false,
  "inactive": []
}
```

`410`: `{ "error": "gone", "reason": "permissions_changed" | "cursor_ahead" }`.

### Snapshot: `GET /dirlocal/snapshot?collection=tasks` + `POST /dirlocal/snapshot/items`

1. `GET /dirlocal/snapshot?collection=tasks` → `{ "cursor": 1240, "primary_key": "id", "keys": ["…", …] }`: имя первичного ключа и все ключи, видимые пользователю (`ItemsService.readByQuery({ fields: [pk], limit: -1 })` под accountability). `cursor` — осевший курсор журнала, зафиксированный **до** чтения ключей.
2. `POST /dirlocal/snapshot/items` с `{ "collection": "tasks", "keys": [...] }` (не больше `DIRLOCAL_MAX_BATCH`) → `{ "data": [...] }` через `readMany` под accountability. Ключей, удалённых или ставших невидимыми между шагами, в ответе нет — их удаление придёт через pull.
3. После snapshot клиент продолжает pull с `cursor`; всё, что изменилось во время snapshot, придёт повторно.

Почему не страницы: offset теряет неизменённые записи, если между страницами удалили предыдущие, а keyset (`pk > after`) Directus не разрешает для `uuid` (`INVALID_QUERY`: нет оператора `_gt`). Список ключей заодно позволяет клиенту при повторном snapshot удалить у себя всё, чего в списке нет.

Ограничение: список ключей отдаётся целиком (100 тыс. UUID ≈ 4 МБ JSON). Для больших коллекций — открытый вопрос §10.

### `POST /dirlocal/compact`

Только для админа. То же, что ночная компактизация; нужен для эксплуатации и тестов. `?retention_days=n` переопределяет срок (тесты передают 0). Ответ `{ "deleted": n, "applied": m }` — удалённые записи журнала и `dirlocal_applied`.

### `POST /dirlocal/push`

Запрос (не больше `DIRLOCAL_MAX_BATCH` мутаций, коллекции только из `DIRLOCAL_COLLECTIONS`, иначе `400`):

```json
{
  "mutations": [
    { "mutation_id": "uuid", "collection": "tasks", "op": "create", "key": "client-uuid", "data": { … } },
    { "mutation_id": "uuid", "collection": "tasks", "op": "update", "key": "…", "patch": { "status": "done" }, "base_version": 1200 },
    { "mutation_id": "uuid", "collection": "tasks", "op": "delete", "key": "…", "base_version": 1200 }
  ]
}
```

`key` у `create` — UUID, созданный клиентом (ADR 0003). `base_version` — курсор клиента в момент правки: всё с `id <= base_version` клиент уже видел. Без `base_version` конфликты не проверяются.

Мутации обрабатываются строго по порядку:

1. Захват `mutation_id`: строка в `dirlocal_applied` с пустым `result`. Уже есть с результатом у этого пользователя — вернуть сохранённый результат, не применять. У другого пользователя — `rejected`, код `MUTATION_ID_TAKEN`. Есть без результата и моложе 60 с (параллельный запрос с той же мутацией) — весь запрос отвечает `409`, `reason: "mutation_in_progress"`, клиент повторит позже. Старше 60 с — сервер упал посреди мутации, она применяется в режиме восстановления (п. 4).
2. `key` и значения полей верхнего уровня, равные ключу записи, которой сервер выдал свой ключ раньше в этом батче, заменяются на `server_key` (ссылки на только что созданную запись с integer-ключом).
3. update/delete: записи журнала по ключу с `id > base_version`. Последняя из них — `d` → `rejected`, код `DELETED`. Записи других акторов, чьи `fields` пересекаются с `patch`, — конфликт: эти поля не применяются, остальные применяются. Delete при любой чужой записи не применяется. Статус `conflict`, `conflicts: [{ field, server_value }]` (для delete — изменённые чужими поля).
4. Применить через `ItemsService.createOne / updateOne / deleteOne` с accountability — как обычный REST-запрос: своя транзакция, события action после коммита, хук журнала пишет изменение, flows видят закоммиченную запись. Общую транзакцию с `dirlocal_applied` не делаем: действия, собранные через `bypassEmitAction`, расширению некуда выпустить (`emitter` в контексте расширения изолирован от core-событий). В режиме восстановления create с ключом клиента и delete сначала проверяют, есть ли запись.
5. Результат записывается в `dirlocal_applied`. Ошибка Directus с HTTP-статусом < 500 (права, валидация, уникальность) → `rejected` с `error: { code, message }`, тоже сохраняется. Другая ошибка снимает захват и прерывает запрос (`500`): клиент повторит батч, уже применённые мутации вернут сохранённый результат.

Ограничение: падение сервера между коммитом мутации и записью результата для create с integer-ключом (ключ выдаёт сервер) при повторе создаст запись второй раз — отличить «применено» от «не применено» не по чему.

Ответ: `{ "results": [{ mutation_id, status: "applied" | "conflict" | "rejected", server_key?, conflicts?, error? }] }` в порядке запроса. `server_key` есть, только если ключ выдал сервер (integer autoincrement); тип — как у первичного ключа. Версию записи клиент узнаёт из следующего pull.

Записи `dirlocal_applied` старше `DIRLOCAL_RETENTION_DAYS` удаляет компактизация.

### Хуки

- `items.create`, `items.update`, `items.delete` (action, после коммита) → запись в `dirlocal_changes` для коллекций из конфига. `payload` обновления даёт список изменённых полей.
- `server.start` → создание таблиц, миграции.
- `schedule('0 3 * * *')` → компактизация: для записей старше `DIRLOCAL_RETENTION_DAYS` оставить только последнюю запись по ключу; tombstones не удалять. Последняя запись по каждому ключу всегда остаётся, поэтому старый курсор не теряет информацию и `410` из-за компактизации не нужен.
- Удаление записи с дочерними связями `ON DELETE CASCADE` / `SET NULL` в отслеживаемых коллекциях: filter `items.delete` (до транзакции) собирает ключи детей, action после коммита журналирует их как `d` / `u`.

### Известные ограничения (в документацию)

- Изменения мимо Directus (прямой SQL, триггеры, вызовы `ItemsService` с `emitEvents: false`) журнал не видит. Каскады `ON DELETE` между отслеживаемыми коллекциями обрабатываются, каскады в неотслеживаемые и из них — нет. Опция: ночная сверка по `date_updated` для коллекций, где поле есть.
- Поля с ограниченными правами: клиент получает только разрешённые — это норма.
- Правила прав со связями (лицензия; например, `notes` видны по `task.assignee`): если меняется связанная запись (задачу переназначили), видимость заметок меняется без записи в журнале по `notes`. Клиент узнает об этом только при следующем изменении заметки или snapshot. Решение — фаза 4.

## 7. Клиент (`@dirlocal/core` + `@dirlocal/expo`)

### Принципы

- Локальная БД — источник правды для UI. Сеть — фоновая синхронизация.
- Мутации сначала пишутся локально (оптимистично) и в outbox, потом отправляются батчами.
- Строка хранится целиком как JSON: таблица на коллекцию `(key TEXT PRIMARY KEY, data TEXT)`, фильтры — через `json_extract`. Схему полей клиент не получает: `/fields` требует права на `directus_fields`, которого у API-only пользователей нет, а выдавать его — значит раскрыть метаданные всех полей. Заодно отпадает миграция локальной схемы при изменении полей на сервере. Имя первичного ключа приходит в ответе snapshot.
- Создание записей офлайн — UUID на клиенте. Для коллекций с integer-ключом сервер выдаёт свой ключ; клиент по ответу push переписывает ключ строки, ссылки на неё в других строках и в outbox (ADR 0003).
- Outbox: мутации пишутся в локальную БД вместе с оптимистичной правкой строки, одной транзакцией. Строки с сервера (pull, snapshot) для ключей с неотправленными мутациями показываются с наложенными поверх мутациями. `base_version` = курсор клиента в момент правки.

### Публичный API (черновик)

```ts
const offline = createOffline({
  directus,                       // клиент @directus/sdk с auth
  collections: ['tasks', 'photos'],
  storage: expoSqlite(),          // адаптер
  realtime: true,                 // подписка на WebSocket как триггер pull
  pollInterval: 60_000,
});

await offline.start();            // snapshot при первом запуске, далее pull

const { data, status } = useCollection('tasks', { where: { project: id } });
await offline.mutate('tasks', { op: 'update', key, patch: { status: 'done' } });
offline.on('conflict', handler);
offline.on('reset', handler);     // 410 Gone → полный снапшот
```

### Файлы

- Метаданные `directus_files` синхронизируются как обычная коллекция.
- Загрузка бинарников — через штатный `/files` из отдельной очереди при появлении сети.
- Скачивание — лениво через `/assets/:id`, кеш в `FileSystem` с LRU.

## 9. Инженерные правила (перенести в CLAUDE.md репозитория)

- TypeScript strict, ESM, pnpm workspaces, changesets для версий.
- Каждое поведение сервера покрывается интеграционным тестом против реального Directus в Docker; юнит-тесты — для `core`.
- Не обходить `ItemsService` прямыми запросами к таблицам пользователя. Прямой knex — только для таблиц `dirlocal_*`.
- Все права — только через `accountability` из запроса; никаких служебных токенов в эндпоинтах.
- Любое изменение контракта API — сначала правка раздела 6 этого документа, потом код.
- Коммиты небольшие, по одной задаче из чек-листа; чек-лист отмечать в этом файле.

## 10. Открытые вопросы

- ~~Имена событий и сигнатуры в 12.5~~ — подтверждены в фазе 0, см. ADR 0001.
- ~~Список изменённых полей при `updateByQuery`~~ — `payload` достаточно: один payload на все keys, его ключи и есть изменённые поля (ADR 0001).
- `dirlocal_config`: коллекция Directus (тратит слот из 25 на Core) или своя таблица/env.
- Каскады `ON DELETE CASCADE` не попадают в журнал (проверено) — собирать дочерние ключи на filter `items.delete` или требовать `SET NULL` (ADR 0001).
- Окно оседания курсора (`DIRLOCAL_SETTLE_MS`) против дырок sequence — подтвердить тестом с задержкой (ADR 0001).
- Сверку по `date_updated` поднять из фазы 4 в фазу 2: журнал теряет изменения при падении между коммитом и вставкой (ADR 0001).
- Политика для M2M/O2M: синхронизировать junction-коллекции как обычные или разворачивать в JSON.
- Максимальный объём снапшота на мобильном: сейчас список ключей отдаётся целиком (≈ 4 МБ на 100 тыс. UUID), данные — пачками. Для больших коллекций нужна потоковая выдача или пагинация ключей с проверкой согласованности.
- Лицензия: MIT для всего или open-core (MIT ядро, платная панель/хостинг).
- Окончательное имя.
